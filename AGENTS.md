- **Status**: Task's Priority-1 `main.js:342 Uncaught ReferenceError: removeCustomDesktopBackground is not defined` confirmed false positive for the **25th consecutive run** (Days 738/741/743/744/745/746/747/750/751/752/753/754/755/755 Run 2/756/757/757 Run 2/758/758 Run 2/759/759 Run 2/759 Run 3/759 Run 4/759 Run 5/759 Run 6/760 Run 1/760 Run 2/760 Run 3/760 Run 4/760 Run 5/775 Run 1) — function defined (`js/main.js:369`), exported on `appServices`, mirrored as `window.removeCustomDesktopBackground`. `grep -c "removeCustomDesktopBackground" js/main.js` → 16; `curl -s https://snugos.github.io/snaw/js/main.js | grep -c` → 16. **No Priority-1 bug to fix this run.** **Found and shipped a real, silent settings-wipe bug** in the freshly-shipped v0.3.99 Track Freeze with Crossfade module (`js/TrackFreezeCrossfade.js`, committed `47eea85` ~7.5h before this run): `loadSettingsFromStorage()` wrapped the entire localStorage enumeration loop in a single try/catch that called `JSON.parse(raw)` for every prefixed key. A single corrupt JSON entry (e.g. from a user manually editing localStorage, a future schema change, a partial write from a tab crash, or a browser that stores `null` for a removed key) would throw on the first bad entry, abort the entire loop, and the outer catch would log a single warning — leaving every other track's crossfade setting un-loaded for the rest of the session, with the user-visible symptom of "I set crossfade to 250ms last week and the picker now says 100ms default." Worse: each subsequent page load would re-trigger the same abort, so the bad entry permanently shadowed the rest of the saved settings until the user manually cleared that one key. 36-line additive fix in `js/TrackFreezeCrossfade.js:loadSettingsFromStorage`: (a) snapshot the prefixed keys first into a local `keys` array, with the outer try/catch now only guarding the enumeration step (and short-circuiting to return on a total failure); (b) walk the snapshot in a separate loop where the `JSON.parse` + `trackSettings.set` is wrapped in its own per-entry try/catch, so a corrupt entry is logged (`Skipping corrupt setting for track ${trackId}: <reason>`) and skipped, while the rest of the saved settings load cleanly. **No APP_VERSION bump** — small defensive fix to a ~7.5h-old feature, and the bug is silent (no error toast, no console error visible to a typical user — only a single `console.warn` that no one is going to notice in a busy DAW console).
